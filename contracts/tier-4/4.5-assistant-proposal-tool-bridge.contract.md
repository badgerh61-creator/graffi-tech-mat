# Tier 4.5 — Assistant Proposal → Tool Bridge

## Purpose
Allow assistant proposals to be applied ONLY via authoritative Studio tools.

## Key Rule
Assistant output is never executable by itself.
It becomes executable only after:
1) validation
2) user confirmation
3) tool registry authorization
4) flow graph approval
5) draft ownership lock

## Proposal Shape (canonical)

{
  "proposal_id": "uuid",
  "snapshot_id": "int",
  "station": "tuning",
  "tool": "UPDATE_ENGINE_CONFIG",
  "payload": { "boost": 1.2 },
  "rationale": "text",
  "risk_level": "low|medium|high",
  "metrics_preview": { ...optional... }
}

## API

POST /assistant/proposals/apply

Request:
{
  "proposal_id": "uuid",
  "snapshot_id": "int",
  "confirm": true
}

## Preconditions
- confirm == true
- proposal exists
- proposal.snapshot_id matches request snapshot_id
- snapshot.status == "draft"
- user holds draft lock
- tool exists in registry
- tool allowed in current station/mode
- flow allows tool in sequence

## Behavior
- execute tool via Studio kernel executor (same as UI tools)
- create new draft snapshot (child)
- record audit event: assistant.proposal.applied
- record audit event: snapshot.tuning_updated (from tool)
- return new snapshot id

## Forbidden
- assistant applying without confirm
- assistant applying without lock
- assistant bypassing tool registry
- assistant mutating completed snapshots
