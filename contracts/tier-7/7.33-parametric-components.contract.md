# Tier 7.33 — Parametric Components (Governed, Deterministic)

## Purpose (LOCKED)
Add a parametric component layer so users can edit reusable "parts" via
parameters, and commits compile deterministically into governed tool ops.

## Component Storage (Authoritative)
Stored in snapshot.body_state:
body_state["components"] : list[Component]

Component:
{
  "id": "cmp-uuid-or-slug",
  "kind": "wheel" | "spoiler" | "ride_height" | "widebody" | "custom",
  "name": "string",
  "enabled": true,
  "target_id": "object::mesh_path" | null,
  "params": { ... },
  "version": 1
}

## Deterministic Compilation
A component commit compiles into a list of tool ops (no randomness):
ops = compile(component_kind, params, target_id)

Each op is a normal governed tool payload:
{
  "tool": "TRANSLATE" | "ROTATE" | "SCALE",
  "station": "geometry",
  "payload": {...}
}

## Tool: APPLY_COMPONENT (UI-level tool)
Frontend emits a single "APPLY_COMPONENT" proposal:
{
  "tool": "APPLY_COMPONENT",
  "station": "geometry",
  "payload": {
    "component_id": "cmp-...",
    "next_params": {...},
    "target_id": "object::mesh_path" | null
  }
}

Backend evaluate/apply:
- loads current snapshot
- finds component by component_id
- builds "next component" with next_params
- compiles to ops
- runs constraint evaluation (Tier 7.32) against each compiled op
- if ok, apply executes ops by calling the existing governed tool executor
- snapshot child created as usual

## Invariants
1) No direct snapshot mutation in UI.
2) Compilation is deterministic.
3) Apply must be blocked if any compiled op violates constraints.
4) Component list is persisted only through the governed snapshot mutation result.
5) If component_id missing -> 404/409 (invalid proposal)

## Forbidden
- arbitrary code execution
- nondeterministic compilation
- bypassing proposal evaluation
