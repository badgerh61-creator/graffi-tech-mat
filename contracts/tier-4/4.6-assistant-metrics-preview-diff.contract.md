# Tier 4.6 — Metrics Preview + Diff for Assistant Proposals

## Purpose
Make assistant proposals "smart" and trustworthy by attaching deterministic metrics previews
and enforcing payload immutability at apply time via payload_hash.

Tier 4.6 upgrades Tier 4.5 by adding:
- POST /assistant/proposals/preview
- payload_hash verification during apply

This provides:
- baseline metrics
- preview metrics
- diff
- risk notes
- deterministic behavior (same inputs -> same output)
- zero mutation (preview never writes)

---

## Definitions

### Proposal (canonical)
A proposal is a structured description of a tool invocation against a draft snapshot.

Fields:
- snapshot_id: int
- station: str
- tool: str
- payload: object
- rationale: optional string
- risk_level: low|medium|high (optional)

### Metrics
Tier 4.4 performance metrics output.

### Preview Result (Tier 4.6)
Contains:
- baseline: metrics computed from current snapshot state
- preview: metrics computed from state after applying the proposal payload in a pure sandbox
- diff: derived changes between baseline and preview
- risk_notes: list[string] derived from deterministic rules
- payload_hash: sha256 canonical hash of {snapshot_id, tool, payload}

---

## API

### POST /assistant/proposals/preview

Request:
{
  "snapshot_id": 123,
  "proposal": {
    "station": "tuning",
    "tool": "UPDATE_ENGINE_CONFIG",
    "payload": { ... }
  }
}

Preconditions:
- Snapshot exists
- Snapshot.status must be "draft" OR "completed" (preview allowed on both)
- Proposal must reference a registered tool (Phase T registry)
- Tool must be previewable (Tier 4.6 only supports preview for tuning tools)

Behavior:
- Compute baseline metrics using Tier 4.4 metrics engine
- Compute preview metrics by applying proposal payload in a pure sandbox (no DB writes)
- Compute diff (key-by-key numeric diffs where applicable)
- Produce risk_notes deterministically based on diff and thresholds
- Compute payload_hash deterministically
- Return the full preview object

Failure Modes:
- 404 snapshot not found
- 422 invalid proposal shape OR tool not previewable OR tool not registered

Response 200:
{
  "baseline": {...},
  "preview": {...},
  "diff": {...},
  "risk_notes": [...],
  "payload_hash": "..."
}

## Apply-time Hash Enforcement (Upgrade Tier 4.5)

When applying a proposal via Tier 4.5 apply endpoint:

POST /assistant/proposals/apply

Request (Tier 4.6 upgrade):
{
  "proposal_id": "uuid",
  "snapshot_id": 123,
  "confirm": true,
  "payload_hash": "sha256..."
}

Preconditions (in addition to Tier 4.5):
- payload_hash must match server-computed hash of current proposal {snapshot_id, tool, payload}
- if mismatch -> 409 conflict ("Proposal payload hash mismatch")

Rationale:
Prevents stale proposal application and guarantees what user previewed is what gets applied.

---

## Invariants (Locked)

1. Preview endpoint is read-only (no DB writes)
2. Preview is deterministic (same snapshot + same proposal -> same result)
3. Hash is deterministic and canonical (stable JSON normalization)
4. Apply rejects hash mismatch (409)
5. Preview does not bypass tool registry or flows; at minimum tool must be registered
6. Preview never mutates snapshots, even drafts

---

## Out of Scope
- Simulation
- Any randomness
- Auto-apply
- Non-tuning tools (unless explicitly added later)
